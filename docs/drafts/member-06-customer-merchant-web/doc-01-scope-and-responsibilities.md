## 1. Purpose & Perspective

I am Sajini, Member 6, responsible for the **Customer & Merchant Frontend** in SwiftDrop. My domain encompasses the primary web portal interfaces that empower external customers to quote, book, and track their shipments, and provide commercial merchants with self-service tools to manage bulk orders, integration credentials, and event webhooks.

I will build my capabilities inside the unified React Single-Page Application (SPA) located at `web/`, specifically within the isolated feature directory `web/src/features/customer-merchant/`. This document formally specifies the boundaries, in-scope functional responsibilities, cross-module ownership matrix, and inviolable engineering standards governing my frontend domain.

## 2. In-Scope Functional Responsibilities

My feature domain covers the following core capabilities:

### 2.1 Customer Onboarding & Authentication UI
- **Customer Registration:** Dedicated self-registration form (`/auth/register`) capturing customer full name, email, password, and mobile phone number, interfacing with `POST /api/v1/auth/register` (Member 1).
- **Shared Authentication Shell:** Integration with the shared login interface (`/auth/login`) supporting credential validation and initiating the Google OIDC authorization code flow (`/auth/google`) with Member 1.
- **In-Memory Session Handling:** Storing short-lived JWT access tokens strictly in React in-memory state (`AuthContext`), while relying on browser-managed HttpOnly refresh cookies for background token rotation (`POST /api/v1/auth/refresh`).

### 2.2 Four-Step Customer Booking Wizard (`/portal/book`)
- **Step 1: Contact & Address Entry:** Sender address (pre-filled from authenticated profile with override capability) and recipient contact details (full name, phone number, delivery address, city, and delivery zone).
- **Step 2: Parcel Dimensions & Zones:** Input fields for package weight in kilograms (`weight_kg`), dimensions in centimeters (`length_cm`, `width_cm`, `height_cm`), package description, and zone selection. Client-side form validation is powered by `react-hook-form` and `zod`.
- **Step 3: Instant Fee Quotation:** Invoking Member 2's authoritative pricing endpoint (`POST /api/v1/pricing/quotes`), rendering a transparent breakdown (base tariff, weight surcharge, volumetric adjustments, total in LKR cents), and caching the returned `quote_id` (valid for 15 minutes).
- **Step 4: Confirmation & Idempotent Submission:** Client-side generation and retention of a UUIDv4 idempotency key, submitting `POST /api/v1/parcels` with the `Idempotency-Key` header and `{ "quote_id": "...", ... }`. Upon success, displaying the authoritative tracking number (`SD-YYYYMMDD-XXXXX`) generated by the backend and direct links to tracking and receipts.

### 2.3 Public & Authenticated Live Shipment Tracking
- **Public Tracking View (`/track/:trackingNumber`):** Anonymous tracking screen allowing anyone with a valid tracking identifier to monitor progress. Strictly adheres to privacy masking rules (SEC-016): only milestone statuses, timestamps, and city/province are displayed; sender details, recipient phone numbers, full street addresses, and proof photos are completely redacted.
- **Authenticated Tracking View (`/portal/tracking`):** Enhanced view for logged-in customers and merchants displaying full delivery history and authorized parcel details.
- **Real-Time Milestone Updates (`useSSE`):** Custom resilient Server-Sent Events hook streaming updates from `/api/v1/tracking/public/{trackingNumber}/stream` (Member 5), featuring initial REST synchronization, event deduplication, automatic reconnect handling, and bounded polling fallback.

### 2.4 Merchant Self-Service Portal (`/portal/merchants/*`)
- **Merchant Application Screen:** Submission form (`/portal/merchants/apply`) for business onboarding (`POST /api/v1/merchants/applications`), displaying application status (`PENDING`, `APPROVED`, `REJECTED`, `SUSPENDED`).
- **Merchant Order Management (`/portal/merchants/orders`):** Tenant-scoped order overview with server-side pagination, status filtering, and individual order dispatch.
- **CSV Batch Order Upload UI:** Browser-based CSV file parser validating required columns client-side before dispatching sequential idempotent booking requests to the backend.
- **API Key Management (`/portal/merchants/api-keys`):** Interface for generating and revoking machine-to-machine API keys (`sd_live_*`). Newly generated keys are presented in a dedicated one-time copy modal with explicit persistence prohibitions.
- **Webhook Management (`/portal/merchants/webhooks`):** Endpoint registration, event subscription selection, secret rotation, and one-time display modal for webhook signing secrets (`whsec_*`).

### 2.5 Automated E2E Test Compatibility
- Inclusion of explicit `data-testid` attributes on all form inputs, buttons, timeline containers, and status badges as agreed with Member 10 for automated Playwright end-to-end verification.

## 3. Out-of-Scope Responsibilities

To maintain strict modular isolation and adhere to DDD boundaries, the following capabilities are explicitly out of scope for Member 6:

1. **Dispatcher Board & Fleet Operations:** Dispatching parcels, manual courier assignment, fleet load management, and zone configurations are exclusively owned by Member 7 (`web/src/features/dispatcher-admin/`).
2. **Courier Mobile Workflow & Proof of Delivery (POD):** Courier task lists (`/courier/tasks`), GPS simulation, barcode scanning, and signature/photo POD uploads are owned by Member 7.
3. **Infrastructure, Ingress & Container Packaging:** Writing the production `web/Dockerfile`, authoring Nginx configuration templates, Traefik edge ingress routing, and Kubernetes manifests are owned by Member 9 (DevOps).
4. **Client-Side Tariff & Fee Calculations:** Strictly forbidden by Engineering Standards. The frontend never calculates delivery charges or volumetric weight independently; all pricing is fetched authoritatively from Member 2.
5. **Client-Side Parcel State Machine Transitions:** The frontend never decides valid parcel lifecycle transitions (e.g. advancing from `CREATED` to `PICKED_UP`); all transitions are evaluated by Member 2's Go aggregate root.
6. **Authoritative Identity, Token Issuance & Credential Storage:** Password hashing (Argon2id), JWT issuance, and database persistence of user identities belong strictly to Member 1 (`core-api/internal/identity/`).
7. **Message Broker, Outbox Relay & Webhook Delivery:** RabbitMQ queue topologies, publishing outbox events, and HTTP webhook retries are owned by Member 8.

## 5. Inviolable Architectural & Security Rules

1. **Zero Client-Side Pricing:** All delivery fees displayed to the user must originate from `POST /api/v1/pricing/quotes`. The returned `quote_id` must accompany the booking creation request. The frontend never computes prices, nor does it trust any fee passed via URL query parameters or hidden form fields.
2. **Server-Generated Tracking Numbers:** Tracking numbers (`SD-YYYYMMDD-XXXXX`) are generated exclusively by Member 2 upon parcel creation. The frontend never fabricates or infers a tracking identifier.
3. **Dual-Token Authentication Security (ADR-003):** Access tokens are short-lived (15 minutes) and stored **only in memory** within React `AuthContext`. Refresh tokens are transmitted exclusively via `HttpOnly`, `SameSite=Strict`, `Secure` cookies. No tokens are ever written to `localStorage` or `sessionStorage`.
4. **Public Tracking Privacy Masking (SEC-016):** Public visitors viewing `/track/:trackingNumber` must never see recipient phone numbers, full street addresses, sender details, internal notes, or proof-of-delivery attachments. Only milestone statuses, timestamps, and destination city/province may be displayed.
5. **Separation of Merchant Browser Auth vs. M2M API Keys:** Logged-in merchant users access the portal using their human JWT Bearer session (`tenant_id` claim). Machine-to-machine API keys (`sd_live_*`) are strictly for server-to-server integrations; the browser never uses `X-API-Key` for dashboard navigation.
6. **One-Time Secret Display Modal:** Newly generated API keys (`sd_live_*`) and webhook secrets (`whsec_*`) are displayed exactly once in a modal with clear copy/save warnings. They are never cached, saved to local storage, or printed to browser logs.
7. **Idempotency Guarantees:** Every parcel booking and merchant order creation dispatches a UUIDv4 `Idempotency-Key` header. Retries of the same logical submission reuse the exact same key.
